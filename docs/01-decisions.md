## 1. Décisions

### Stockage et exécution

| # | Décision | Alternatives écartées | Pourquoi |
|---|---|---|---|
| D1 | **Base SQLite dans une release GitHub** (`db`) : asset courant compressé, plus un instantané par semaine | Fichier commité dans le dépôt ; `.gz` commité ; artefacts ou cache Actions ; PostgreSQL hébergé | Volume mesuré : 82 Mo pour le périmètre v1, au-dessus de l'avertissement GitHub (50 MiB) et proche du blocage (100 MiB). Un commit quotidien d'un binaire gonfle l'historique. Les artefacts et le cache ne sont pas durables. Un PostgreSQL hébergé contredit « zéro serveur ». Release : moins de 2 GiB par fichier, pas de limite totale (vérifié). Détail dans architecture §5 |
| D2 | **Une exécution quotidienne** (`schedule` à 05:47 UTC), sérialisée par `concurrency` | Plusieurs exécutions par jour ; déclenchement par source | CONTEXTE : quotidien. Les sources publient au mieux chaque semaine. L'horaire hors début d'heure suit la documentation GitHub. La sérialisation évite deux écritures concurrentes sur la base |
| D3 | **Une transaction par source**, l'échec d'une source n'arrête pas les autres ni la publication du site | Tout ou rien sur l'ensemble des sources | Une panne de Sentinelles ne doit pas bloquer l'OMS. Le site affiche les dernières données avec leur date |

### Modèle de données

| # | Décision | Alternatives écartées | Pourquoi |
|---|---|---|---|
| D4 | **Révisions par versions ajoutées** dans `observations` (`version`, `valid_from`, `valid_to`) avec un index unique partiel (une seule version courante) | Écraser la valeur ; table d'historique séparée ; versions sans `valid_to`, lues par fonction de fenêtre | Écraser perd l'historique et fausse tout backtest futur. Une table séparée double les écritures à synchroniser. `valid_from`/`valid_to` donnent la valeur connue à une date D par une requête simple (démontré dans la validation §4.2) |
| D5 | **`reports` = état courant ; historique des DON dans `raw_payloads`** | Versionner `reports` comme `observations` | Un DON modifié est un texte retouché, pas une série révisée. Le brut horodaté suffit pour retracer, avec une ligne par contenu distinct (sha256) |
| D6 | **Identité d'un DON : `Id`** (GUID) ; `DonId` stocké sans contrainte d'unicité ; `UrlName` unique | `DonId` ou `UrlName` comme clé | Décision de phase 0. `Id` est unique sur 3199/3199 ; `DonId` a 14 doublons. | D7 | **Date de publication = `PublicationDateAndTime`**, avec un drapeau `date_quality` | `PublicationDate` ; date déduite de `UrlName` | `PublicationDate` est faux pour 1360 enregistrements. `PublicationDateAndTime` est cohérent avec l'année du `DonId` sauf dans 11 cas, et avec le titre sauf dans 2. `UrlName` a trois formes différentes (architecture §3.4) |
| D8 | **Titre = `OverrideTitle` si `UseOverrideTitle` et non vide, sinon `Title`** | Toujours `Title` | C'est le `<h1>` affiché sur who.int (vérifié sur 2 DON). 170 enregistrements ont un `OverrideTitle` différent de `Title`, dont un « Chikungunya - France » dont le `Title` cite Mayotte et La Réunion |
| D9 | **Remplacée par D23 (phase 1b).** Ancienne décision : chiffres en colonnes de `reports`, un couple cas/décès par DON | | |
| D10 | **Table `report_countries`** (ISO 3166-1 alpha-3, au plus un pays principal) en plus de `geo_scope` | Une seule colonne pays ; liste JSON dans `reports` | Des DON couvrent plusieurs pays. Une colonne unique perd l'information ; le JSON est moins portable et moins indexable |
| D11 | **Table `series`** séparée d'`observations` (écart à la liste de tables demandée) | Répéter dans chaque observation source, jeu, mesure, zone et âge | La clé naturelle d'un point a 6 colonnes. Une série la porte une fois ; détection d'anomalies, unicité et requêtes travaillent sur `series_id`. Le niveau géographique fait partie de la clé, car les codes INSEE de région et de département se recouvrent (`11`) |

| D13 | **Valeurs énumérées en `CHECK (... IN (...))`**, en français sans accents (`valide`, `incertain`, `officielle`) | Tables de référence ; types `ENUM` PostgreSQL | Listes courtes et stables ; portable tel quel ; aucun problème d'encodage |

### Bruts, types et portabilité

| # | Décision | Alternatives écartées | Pourquoi |
|---|---|---|---|
| D14 | **Bruts dédupliqués par sha256** ; JSON OMS en clair (`body_text`), exports volumineux compressés (`body_gzip`) ; corps purgeables (`purged_at`) en gardant les métadonnées, **seulement pour les exports CSV d'Odissé** (I53) : JSON OMS, réponses Sentinelles et réponses du catalogue Odissé sont conservés sans limite (relecture D31, preuves de licence D30). `raw_payloads` stocke des contenus, pas une chronologie : la chronologie d'un DON est dans `report_versions` (D26) | Tout garder en clair ; bruts hors base (fichiers en release) | En clair, le JSON OMS reste lisible et interrogeable : 15 Mo au total, environ 2,5 Mo de plus par an. Les exports Odissé sont de gros fichiers re-exportés chaque semaine. La purge limite la croissance sans perdre la trace (hash, date, URL) |
| D15 | **Tables `STRICT`, dates en `TEXT` ISO 8601 UTC, aucun trigger, aucun `DEFAULT` calculé, aucune fonction de date dans les requêtes.** Révisé en phase 1b : les fonctions de date et `json_valid` sont **permises dans les `CHECK` de validation** (I2, I33, I59). Les règles entre lignes sont vérifiées par la vue `controle_invariants` (D25) | Types `DATE`/`TIMESTAMP` déclarés (affinité NUMERIC en SQLite) ; triggers pour fermer les versions ou imposer les invariants entre lignes ; `CHECK LIKE` de forme (phase 1) | `STRICT` refuse un mauvais type, ce qui protège un mainteneur seul. Un `CHECK LIKE` accepte `2026-99-99t99:99:99z` (constat 11 du relecteur). Les `CHECK` de validation ne posent pas de problème de portabilité : en PostgreSQL, les types `TIMESTAMPTZ`, `DATE` et `JSONB` les remplacent, et le `CHECK` du calendrier ISO se réécrit avec `EXTRACT` (architecture §6). Les requêtes, elles, restent sans fonction de date. I26 et I50 ne sont pas imposés par la base : ils sont vérifiés par la relecture des bruts (D31), sans trigger (décidé le 2026-10-14) |
| D16 | **Version de schéma par `PRAGMA user_version`** et fichiers de migration numérotés, appliqués par un petit script | Alembic ou un ORM | Pas de sur-ingénierie pour un seul mainteneur et un seul moteur en v1. À remplacer par une table de migrations lors d'un passage à PostgreSQL |

### Site, alertes et périmètre

| # | Décision | Alternatives écartées | Pourquoi |
|---|---|---|---|
| D17 | **Le site lit des exports JSON produits par Python**, pas la base SQLite | Lire SQLite depuis Astro (module natif Node) | Garde le côté Node simple, sans dépendance native ; contrôle exactement ce qui est publié ; respecte la limite Cloudflare de 25 MiB par fichier |
| D18 | **Déploiement Cloudflare Pages par envoi direct** (`wrangler`) depuis Actions | Intégration Git de Cloudflare (build chez Cloudflare) | Le build a besoin de la base, téléchargée dans Actions. Hébergeur choisi en phase 0 |
| D19 | **Alertes livrées « au moins une fois », avec déduplication par la clé `(channel, dedup_key)`.** Une alerte est écrite (`a_envoyer`) dans la même transaction que l'événement qui la déclenche (I46). Elle passe à `envoyee` seulement après une réponse `ok` de Telegram. La clé est déterministe (I45). Les alertes partent avant l'envoi de la base, qui a lieu une seule fois par exécution | Livraison « exactement une fois » ; envoi des alertes après l'envoi de la base ; second envoi de la base après les alertes | « Exactement une fois » est impossible ici : l'appel à Telegram et l'écriture en base ne sont pas atomiques, et `sendMessage` n'a aucune clé d'idempotence (documentation de l'API Bot lue le 2026-10-13 ; une réponse réussie renvoie le `Message`). Garanties réelles : **aucune alerte perdue**, car la ligne existe avant l'envoi et une alerte non confirmée est retentée ; **aucun renvoi** d'une alerte marquée `envoyee` dans la base de départ. **Doublon possible** dans les autres cas (R14, démontré par CE-C2). Un second envoi de la base après les alertes réduirait la fenêtre sans la fermer, pour un envoi de base de plus par jour : **écarté le 2026-10-14, le doublon rare est accepté** |
| D20 | **Anomalies : production seulement, hausses seulement** (`CHECK observed_value > threshold_value`). Résultats de backtest hors base | Stocker aussi les backtests (colonne `mode`) | Les backtests sont des analyses ponctuelles (rapports dans `docs/`). Les mélanger aux anomalies de production risquerait des alertes erronées |
| D21 | **Aucune donnée personnelle dans la base** | Stocker abonnés et destinataires | La base est publique (release d'un dépôt public). Les e-mails de la v2 (double opt-in, RGPD) iront dans un stockage séparé, à concevoir en v2 |
| D22 | **Zones géographiques distinctes : `FR` (France entière) et `FR-MET` (métropole)** | Un seul code `FR` | Sentinelles ne couvre que la métropole (vérifié en phase 0). Mélanger les deux fausserait toute comparaison |

### Phase 1b : décisions issues de la revue

| # | Décision | Alternatives écartées | Pourquoi |
|---|---|---|---|
| D23 | **Chiffres des rapports dans une table `report_figures`** (remplace D9). Une ligne par chiffre, définie par : mesure (`cas`, `deces`) ; pays du rapport ou ensemble du rapport ; définition de cas ; période `[period_start, as_of]` ; version brute lue. Méthode, statut et phrase source sont portés par chaque chiffre. Les chiffres affichés sont ceux de la vue `report_figures_current` | Rester à un couple cas/décès en colonnes de `reports` en v1 (D9) | Sur l'échantillon, 3 DON sur 5 contiennent plus d'un couple de chiffres. Par exemple, `2024-DON528` couvre 5 pays avec au moins 4 dates « au » différentes. CE-D1 : trois pays écrits, un seul conservé. Passer à une table après la phase 3 imposerait de reconstruire `reports`, car SQLite refuse `DROP COLUMN` sur une colonne citée par un `CHECK` de table (CE-D2). Il faudrait aussi revalider à la main des chiffres dont le sens est ambigu (total ? pays principal ? cas confirmés ?). Coût immédiat : une table, une vue, 6 invariants ; l'extraction reste aussi difficile. Comparaison détaillée : `docs/01b-arbitrage.md` §D |
| D24 | **« Écart 0 » OMS mesuré sur les DON présents dans l'API au moment de l'exécution ; DON absents suivis à part.** La présence est rattachée aux exécutions par les colonnes `first_seen_run_id`, `last_seen_run_id` et `removed_run_id`, qui remplacent les horodatages `first_seen_at`, `last_seen_at` et `removed_at`. `reports.source_modified_at` est supprimé : la valeur reste dans le brut. Le compteur d'absences n'est pas stocké : il est calculé par la vue `reports_presence` | Formulation de CONTEXTE prise à la lettre (« DON ingérés = DON du site ») ; compteur d'absences stocké dans `reports` ; `seen_count = reports_active` (phase 1) | La formulation de CONTEXTE ne peut pas tenir dès que l'OMS retire un DON. Le nombre de DON ingérés reste au-dessus du total du site pour toujours, et la règle de la phase 1 est fausse pendant le délai de 3 exécutions (CE-A1). Un compteur stocké pourrait diverger des exécutions, alors qu'un compteur calculé ne le peut pas. Rattacher la présence aux exécutions rend le retrait vérifiable (I9, I10). Formulation complète : `docs/01b-arbitrage.md` §2. **Validée par le porteur du projet le 2026-10-14.** Pas de contrôle manuel périodique du site : une vérification unique en phase 2 (la liste du site lit-elle la même API ?). **Retrait (décidé le 2026-10-14)** : seuil de 3 exécutions complètes conservé ; un DON « absent » reste affiché ; la page d'un DON retiré reste en ligne avec la mention « retiré par l'OMS le … » (phase 4) |
| D25 | **Règle de placement des invariants.** Les règles exprimables en SQL vont en SQL : `CHECK`, unicité, clé étrangère éventuellement composite, sur des colonnes existantes. Les autres vont en Python avec un test nommé, et dans la vue `controle_invariants` quand elles sont vérifiables après coup. La base n'est envoyée que si `integrity_check` est `ok`, si `foreign_key_check` et `controle_invariants` sont vides et si l'asset tient sous le seuil de taille (I58) | Triggers ; dénormaliser `source_code` et `period_type` dans `observations` pour écrire des clés composites ; tout en Python | Les triggers ne sont pas portables tels quels (PostgreSQL demande une fonction par trigger) et sortent de la logique du code testé. La dénormalisation ajouterait deux colonnes répétées sur environ 500 000 lignes, qu'il faudrait garder cohérentes. Avec la vue, toute violation d'un invariant entre lignes est vue avant publication. 49 contre-exemples rejoués : 25 rejetés par la base, 18 détectés par un contrôle, 1 laissé à la relecture des bruts (I26, D31), 1 doublon par conception (R14), 3 états cohérents, 1 sans objet. 22 preuves du relecteur rejouées : 8 rejetées, 5 détectées, 1 doublon par conception, 4 états cohérents après correction, 4 constats hors schéma. Détail : `docs/01b-preuves.md` |
| D26 | **Chronologie des contenus d'un DON dans `report_versions`** : une ligne par changement du contenu courant (version, brut, exécution), y compris un retour à un contenu déjà archivé. Un DON a changé si le hash reçu diffère de celui du contenu **courant** (I51, I52) | Supprimer la déduplication des bruts (un brut par apparition) ; versionner `reports` comme `observations` | Constat 5 du relecteur : avec la déduplication par hash, une suite A → B → A ne garde que 2 contenus et perd la date du retour à A (K5). Garder la déduplication économise le stockage ; la table de chronologie, petite (~3 200 lignes plus les modifications), rend chaque changement daté. `reports.raw_payload_id` reste le raccourci vers le contenu courant ; la vue vérifie qu'il est égal à la dernière version |
| D27 | **Licence relevée par jeu de données (`datasets`)**, avec sa preuve (`catalogue_api` et brut archivé, ou `verification_manuelle`), sa date et un indicateur `is_publishable`. Toute série cite un jeu ; aucune observation pour un jeu non publiable (I54). Le référentiel inscrit les 9 jeux vérifiés en phase 0 et les 7 jeux exclus faute de licence | Licence au niveau du fournisseur seulement (`sources.license_name`) ; colonne de licence dans `series` | Constat 9 : Odissé héberge des jeux sous des licences différentes, ou sans licence ; la phase 1 affichait « Licence Ouverte 2.0 » pour un jeu exclu (K9). La base étant publique, y stocker des observations d'un jeu non publiable reviendrait à les publier. Une table par jeu évite de répéter la licence dans chaque série |
| D28 | **Statut de chaque valeur (`observations.value_status`) et domaine par série (`series.value_min`).** Statuts : `publiee`, `provisoire`, et pour une valeur absente `retiree`, `non_diffusee`, `secret_statistique`, `absente_sans_motif`. Un changement de statut est une révision (I50) | Une seule valeur NULL sans motif ; un booléen « provisoire » ; ramener les valeurs négatives à 0 | Constat 10 : la phase 1 confondait les motifs d'absence et acceptait -5 hors de son intervalle (K10a, désormais rejeté par I27). Le statut sépare aussi la provisionalité d'une valeur de la fiabilité de la source (constat 9). Une valeur négative n'est pas corrigée : elle est refusée par le contrôle si la série l'interdit (I56) et acceptée sinon (correction légitime d'un cumul) |
| D29 | **Rétention et taille de la base** : seuls les exports CSV d'Odissé sont purgeables (I53) ; JSON OMS, réponses Sentinelles et catalogue Odissé conservés sans limite (volume Sentinelles à mesurer en phase 2, alerte au-delà de 50 Mo par an) ; exports Odissé purgés après 26 semaines (Q1), puis `VACUUM`. Contrôle avant envoi : alerte au-delà de 1 Gio compressé, envoi bloqué au-delà de 1,5 Gio (I58). Instantanés quotidiens gardés 7 jours, en plus des instantanés hebdomadaires (R5) | Aucune purge ; dimensionnement fixé dès maintenant sur des chiffres synthétiques | Constat 13 : sans purge, le scénario haut du relecteur (10 Mo d'exports par semaine) atteint environ 2,7 Go en 5 ans, au-delà des 2 GiB d'un asset. Le volume réel des exports est inconnu (non mesuré) : les seuils protègent l'envoi en attendant la mesure. Mesure actuelle de la base synthétique sans exports : 86,7 Mo, 10,5 Mo compressés (validation §5). **Rétention et seuils validés par le porteur du projet le 2026-10-14** |
| D30 | **Changement de licence d'un jeu après collecte : les données déjà collectées restent.** `datasets` porte une fenêtre de publication (`publishable_since`, `not_publishable_since`). À un changement de licence : collecte arrêtée, `not_publishable_since` = date du constat, alerte. Le contrôle I54 ne bloque que les observations collectées après cette date, et toute observation d'un jeu jamais publiable. Le site indiquera « collectées sous Licence Ouverte 2.0 jusqu'au … » (phase 4). Les réponses du catalogue, preuves de l'ancienne licence, ne sont jamais purgées (I53) | Retirer les données de la base publique ; bloquer l'envoi jusqu'à une décision humaine (premier passage) | La Licence Ouverte 2.0 accorde le droit de réutilisation « sans limite de durée » (`docs/00-sources.md` §4.3) : des données obtenues sous cette licence restent réutilisables. Ce n'est pas un avis juridique. Ne vaut pas pour Sentinelles, dont les conditions sont propres : un changement impose de leur écrire. Démontré par CE-L1 et CE-L2. Décidé le 2026-10-14 |
| D31 | **Contrôle de relecture des bruts** (I26, I50, I60). Chaque version d'observation cite le brut d'où vient sa valeur (`raw_payload_id` obligatoire). Le code de lecture des sources est rejoué et comparé à la base : à chaque exécution sur le dernier brut de chaque jeu (une révision manquée est vue le jour même) ; chaque semaine sur tous les bruts conservés (une valeur réécrite est vue). Un écart déclenche une alerte et bloque l'envoi de la base | Test seul ; trigger SQLite contre la réécriture d'une version fermée | Seule option qui couvre à la fois la réécriture d'une valeur (I26) et la révision manquée (I50), sur les vraies données ; le trigger ne couvre que la première et déroge à D15 ; un test ne vérifie pas la base publiée. Limite : un export Odissé purgé (au-delà de 26 semaines) ne peut plus être relu. Décidé le 2026-10-14 |
| D32 | **Baseline saisonnière sur une fenêtre de dates** (tranche Q9). Références : les semaines situées à ±3 semaines de la même date, sur les 5 années précédentes (jusqu'à 35 valeurs). Au moins 3 années présentes, sinon pas de détection pour ce point. La semaine 53 n'a pas de règle propre : ses voisines servent de références. Le seuil et le détail de la méthode restent à fixer en phase de détection | « Mêmes semaines » au sens strict (CONTEXTE) ; W53 comparée à la moyenne de W52 et W01 | Avec des numéros de semaine, W53 n'a qu'une référence sur 5 ans (K6c). Une fenêtre de ±3 semaines sur 5 ans est le principe des méthodes de type Farrington, courantes en surveillance ; elle traverse W52/W53 → W01 sans cas particulier. Élargit la formulation de CONTEXTE (« mêmes semaines des années précédentes »). Décidé le 2026-10-14 |
| D33 | **Précision des chiffres : colonne `report_figures.precision`** (`exact`, `environ`, `au_moins`, `au_plus`, `fourchette_basse`, `fourchette_haute`), `NOT NULL`, **sans valeur par défaut** (l'extraction doit toujours la renseigner), `CHECK` sur les six valeurs (I62). Une fourchette est stockée en **deux lignes**, une par borne, avec les mêmes colonnes. L'index unique I36 reçoit en plus un « rôle » : `fourchette_basse` et `fourchette_haute` pour les bornes, `point` pour les quatre autres valeurs, si bien que les deux bornes coexistent mais qu'un même chiffre (même version, rapport, pays, mesure, définition, période) n'a qu'une lecture ponctuelle. Borne basse ≤ borne haute : I61 (Python + vue `controle_invariants`). **Contexte** : « about 200 » et « 200 » étaient indiscernables dans les colonnes, et les deux bornes d'une fourchette se heurtaient à l'index I36 (constat de `docs/03-notes.md`). **Impact** : aucune base réelle n'existe encore ni aucune base versionnée, donc pas de migration ; `db/schema.sql` est modifié directement, les INSERT de `db/check_schema.py` et `db/check_invariants.py` reçoivent la colonne (leurs résultats sont inchangés : 49 contre-exemples et 22 preuves, aucun écart) | Mettre la précision dans `evidence` seulement (texte libre, non interrogeable : le site ne pourrait pas écrire « environ ») ; ajouter `environ`, `au_moins`… à `case_definition` (mélange le type de cas et la précision du nombre) ; une table ou deux colonnes `value_low` / `value_high` (casse le modèle « une ligne = un chiffre », l'unicité et les vues `report_figures_current` ; la fourchette n'est qu'un cas rare) ; mettre `precision` telle quelle dans l'index (autoriserait `exact` et `environ` pour le même chiffre, donc deux lectures contradictoires) ; `DEFAULT 'exact'` (une précision oubliée par l'extracteur passerait pour exacte sans erreur : c'est la perte silencieuse que la colonne doit empêcher) ; `CHECK` entre bornes en SQL (trigger refusé, D15) | **Portabilité PostgreSQL** : `CHECK (precision IN (...))` et `NOT NULL` identiques. `PRECISION` est un mot-clé non réservé de PostgreSQL, utilisable comme nom de colonne (à vérifier lors du portage, comme le reste : aucun PostgreSQL n'est installé). L'index sur expression utilise `(CASE ... END)` entre parenthèses, forme qu'exige PostgreSQL pour une expression qui n'est pas un appel de fonction et que SQLite accepte ; `COALESCE` y est déjà accepté sans parenthèses. Aucune fonction de date ajoutée. Cumulé ou nouveau reste porté par `period_start` (NULL = depuis le début de l'événement) : l'étiquetage de la phase 3 a une colonne `cumule_ou_nouveau` qu'aucune colonne du schéma ne reçoit, l'extracteur la traduira en `period_start` |
